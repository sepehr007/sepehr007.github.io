# معماری هم‌تماشا

نقشهٔ کوتاه و به‌روز از اجزای واقعی پروژه. هر تغییری در ساختار باید همین فایل را به‌روز کند.

## نمای کلی

- **فرانت‌اند استاتیک (PWA):** `D:\Site` — HTML + ES Modules + CSS، منتشرشده روی GitHub Pages (`sepehr007.github.io`).
- **بک‌اند اختیاری:** `D:\Site\server` — Fastify 5 روی Node ≥ 22.5 با SQLite داخلی یا MongoDB. سایت بدون آن هم با حالت محلی کار می‌کند و با `assets/data/runtime-config.json` یا `wt.apiBase` به سرور وصل می‌شود.

## فرانت‌اند

| بخش | محل |
| --- | --- |
| صفحات | `index.html` (لندینگ)، `auth.html` (ورود/ثبت‌نام/بازیابی)، `profile.html`، `owner.html` (+ مسیرهای مخفی)، `room.html` |
| طراحی | `assets/css/design-system.css` (توکن‌های واحد) سپس `style.css` و اسکین‌های `-v8` و `owner.css` |
| منطق | `assets/js/` — `core.js`، `i18n.js`، `auth.js`، `api.js`، `site-config.js`، `feature-flags.js`، `lobbies.js`، `room.js`، `player.js`، `net.js`، `voice.js`، `owner*.js` (`owner-center`، `owner-god`، `owner-registry`، `owner-audit`) |
| ذخیرهٔ محلی | `localStorage` (نشست سبک، تنظیمات ظاهر) و IndexedDB (`db.js`: حساب‌ها، لابی‌ها، پیام‌ها، فعالیت، پلن/سفارش) |
| دو زبان | `i18n.js` با کلیدهای fa/en و سوییچ RTL/LTR |
| آفلاین | `sw.js` — کش نسخه‌دار؛ HTML/JS/CSS با `no-cache` از شبکه و fallback کش |

## بک‌اند

- **سرور:** `server/index.js` — CORS، محدودیت نرخ، WebSocket (`/ws`)، مسیرهای REST.
- **مسیرها:** `/api/auth/*` (ثبت‌نام، ورود، تأیید ایمیل، بازیابی، پروفایل، اتصال ایمیل/پیامک مالک)، `/api/lobbies/*`، `/api/billing/*`، `/api/admin/*` (دیتابیس، حسابرسی، نمای پلتفرم، کاربران، اتاق‌ها، پیام‌ها، گزارش‌ها، مالی، آمار، ذخیره‌سازی، تنظیمات و کنترل قابلیت‌ها؛ فقط مالک)، `/api/features`، `/api/settings/public`، `/api/health`.
- **کنترل قابلیت:** `server/features.js` کاتالوگ، وابستگی‌ها، دامنه‌ها (سراسری/کاربر/اتاق/سرور/نقش/پلن)، زمان‌بندی و تاریخچه را نگه می‌دارد؛ `server/platformSettings.js` رجیستری تنظیمات را اعتبارسنجی می‌کند؛ `server/adminGuard.js` نقش مالک و نرخ درخواست را برای همه‌ی مسیرهای پنل اعمال می‌کند. رابط کاربری در `assets/js/owner-god.js` به همین APIها وصل است.
- **حافظهٔ نشست:** Redis در صورت وجود، وگرنه حافظهٔ فرآیند (`server/redis.js`)؛ در حالت SQLite نشست در جدول `sessions` هم ذخیره می‌شود تا ری‌استارت سرور کاربر را بیرون نیندازد. JWT با `jti` که با خروج یا تغییر رمز باطل می‌شود.
- **تنظیمات:** `server/settings.js` — DB-first، متغیرهای env فقط وقتی دیتابیس غیرفعال است؛ رازها هرگز به مرورگر برنمی‌گردند و فقط فلگ `passSet/apiKeySet/twilioTokenSet` برمی‌گردد.
- **ایمیل/پیامک:** `server/mailer.js` (nodemailer + outbox JSONL) و `server/sms.js` (کاوه‌نگار/Twilio/وبهوک + outbox JSONL).
- **حسابرسی:** `server/audit.js` — ثبت عملیات حساس در `audit_logs` با سانسور خودکار کلیدهای حساس.

## دیتابیس

- **SQLite درون‌ساخت (`node:sqlite`)** منبع حقیقت پیش‌فرض است — فایل `server/data/wt.sqlite` (قابل تغییر با `DATA_DIR`/`SQLITE_FILE`).
- **MongoDB/Mongoose** وقتی `MONGO_URI` در دسترس باشد؛ مسیر قبلی دست‌نخورده می‌ماند.
- **لایهٔ مشترک:** `server/database/schema.js` (اسکیمای ~۴۰ جدول + مهاجرت‌های نسخه‌دار)، `server/database/index.js` (اتصال، تراکنش، پشتیبان، خروجی، نگهداری)، `server/userStore.js`، `server/sessionStore.js`، و `server/stores/*` برای لابی/اتاق/مالی.
- جزئیات کامل ساختار، ایندکس‌ها، پشتیبان‌گیری و سیاست نگهداری در `docs/database.md`.

## زمان واقعی

- اتاق: WebRTC مستقیم (P2P) با «میزبان = سرور»؛ چت/پخش/واکنش روی data channel میزبان.
- سرور: هاب WebSocket برای حضور و قواعد قابلیت‌ها؛ Redis در حد نشست/کش/نرخ است، Pub/Sub برای مقیاس چندنمونه‌ای هنوز اضافه نشده.

## سلسله‌مراتب پیکربندی

ترتیب اختیار از بالا به پایین ثابت است و در `server/configHierarchy.js` تعریف شده:

1. **محدودیت امنیتی سراسری** — `SECURITY_MANDATORY_OFF` و `FEATURE_EMERGENCY_OFF`؛ از سطح استقرار می‌آیند و با هیچ تنظیمی باز نمی‌شوند.
2. **محدودیت قابلیت سراسری** — مقادیر `site-config.json`، بازنویسی سراسری دیتابیس و قاعده‌های اضطراری/زمان‌دار.
3. **استحقاق اشتراک** — بازنویسی دامنهٔ `plan` و پلن فعال همان کاربر (خودکار از اشتراک زنده خوانده می‌شود).
4. **مجوز نقش** — بازنویسی دامنهٔ `role`.
5. **پیکربندی سرور** — بازنویسی دامنهٔ `server`؛ اگر اتاق به سروری وصل باشد خودکار اعمال می‌شود.
6. **پیکربندی اتاق** — ستون‌های `room_settings` (چت، صدا، اشتراک صفحه، صف، زیرنویس، فایل محلی) و بازنویسی دامنهٔ `room`.
7. **ترجیح شخصی** — بازنویسی دامنهٔ `user` و سوییچ‌های محلی مرورگر.

قاعدهٔ حل تعارض سقف‌محور است: هر لایه فقط می‌تواند محدودتر کند. اگر لایهٔ بالاتر قابلیتی را ببندد، هیچ لایهٔ پایین‌تری نمی‌تواند بازش کند؛ خاموشی در هر لایه یعنی خاموشی نهایی و وقتی چند لایه هم‌زمان می‌بندند، بالاترین لایه به‌عنوان منبع گزارش می‌شود. «اجازه» در لایهٔ پایین هیچ‌وقت «منع» بالاتر را برنمی‌دارد.

- مثال: چت در سطح سراسری بسته شود، روشن‌کردن دامنهٔ کاربر برای همان شخص هیچ اثری ندارد.
- مثال: اتاقی `chat_enabled = 0` داشته باشد؛ حتی مدیر هم در آن اتاق چت ندارد و منبع «تنظیمات اتاق» گزارش می‌شود.
- مثال: قابلیتی در قفل امنیتی باشد؛ پنل مالک دکمهٔ روشن‌کردن را غیرفعال نشان می‌دهد و API سرور با خطای `security_locked` رد می‌کند. خاموش‌کردن یا حذف بازنویسی مجاز است ولی قفل امنیتی سر جایش می‌ماند.
- سرویس‌های سرور (`/api/features`، گاردهای HTTP و WebSocket) همیشه همین نتیجهٔ نهایی را می‌بینند؛ نه تنظیم خام یک دامنه را.

## اجرای سمت کاربر و سرور

معماری ترکیبی است: هر کاری که به دستگاه کاربر مربوط است همان‌جا انجام می‌شود و سرور فقط چیزهایی را نگه می‌دارد که باید مشترک، قابل‌اعتماد یا ماندگار باشند.

| کار | محل اجرا | توضیح |
| --- | --- | --- |
| رندر پخش‌کننده، پخش ویدیو، کنترل‌های رسانه | مرورگر | `player.js`/`room.js`؛ سرور هیچ فریم یا تنظیم ظاهری پردازش نمی‌کند |
| زیرنویس، انتخاب ترک صوتی، ظاهر زیرنویس | مرورگر | استایل و نمایش کاملاً محلی است |
| صدا و روشنایی شخصی، تم، ظاهر چت، انیمیشن، چیدمان واکنش‌گرا | مرورگر | در `localStorage`/`CSS`؛ هیچ درخواستی به سرور نمی‌رود |
| وضعیت رابط (تب فعال، پنل شناور، پیش‌نمایش) | مرورگر | ذخیرهٔ موقت محلی؛ در دیتابیس نوشته نمی‌شود |
| اعتبارسنجی فرم‌ها | هر دو | نسخهٔ مرورگر فقط برای تجربهٔ کاربری است؛ سرور دوباره اعتبارسنجی می‌کند |
| ورود، نشست، نقش، مالکیت داده | سرور | `routes/auth.js`, `adminGuard.js` |
| عضویت اتاق، وضعیت مشترک پخش، حضور | سرور + مرورگر | `net.js` پیام را می‌فرستد، سرور اعتبارسنجی/پخش می‌کند |
| پیام چت و تاریخچه | مرورگر (رندر) + سرور (ذخیره) | `ws` پیام را می‌گیرد و در `messages` می‌نویسد؛ تاریخچه ۵۰تایی صفحه‌بندی شده |
| اشتراک، پرداخت، دعوت، مدیریت، حسابرسی | سرور | هیچ تصمیم حساسی به کلاینت سپرده نمی‌شود |
| تنظیمات سراسری و قابلیت‌ها | سرور | رابط محلی فقط نمایش می‌دهد؛ دامنه‌ها سمت سرور حل می‌شوند |
| اشتراک صفحه و WebRTC | مرورگر + سرور | مجوز دوربین/صفحه از مرورگر، سیگنالینگ و گیت‌ها از سرور |

قاعدهٔ اعتماد: بررسی‌های سمت کلاینت فقط UX هستند. هر عملیات محافظت‌شده (پنل مالک، ساخت اتاق، چت، پرداخت) در سرور دوباره با توکن، نقش و قابلیت‌های مؤثر همان لحظه بررسی می‌شود.

صرفه‌جویی منابع:

- نتیجهٔ قابلیت‌ها برای هر زمینه (کاربر/نقش/اتاق/سرور/پلن) تا ۳ ثانیه کش می‌شود (`FEATURE_SCOPE_CACHE_MS`) تا هر پیام چت باعث چند کوئری SQLite نشود؛ هر تغییر بازنویسی همان لحظه کش را پاک می‌کند.
- تنظیمات پلتفرم ۴ ثانیه کش می‌شوند و ذخیرهٔ هر تغییر کش را باطل می‌کند.
- ذخیرهٔ وضعیت پخش حداکثر هر ۹۰۰ میلی‌ثانیه یک‌بار انجام می‌شود و رویدادهای «state» کمتر از آن نادیده گرفته می‌شوند.
- حضور فقط هنگام ورود/خروج پخش می‌شود؛ حرکت ماوس، تغییر صدا، روشنایی و تعامل‌های ظاهری هیچ پیامی به سرور نمی‌فرستند.
- سرویس‌ورکر فایل‌های استاتیک و تصاویر را کش می‌کند و فقط HTML/JS/CSS با `no-cache` تازه می‌شوند.
- وضعیت موقت رابط در دیتابیس ذخیره نمی‌شود؛ فقط داده‌ای که باید مشترک یا ماندگار باشد (پیام، وضعیت پخش، عضویت، سفارش) نوشته می‌شود.

## احراز هویت

- محلی (بدون سرور): PBKDF2 در مرورگر، کد بازیابی یک‌بارمصرف، نشست ۳۰ روزه.
- سروری: bcrypt، JWT کوتاه‌عمر با `jti`، کد ۸ رقمی هش‌شده برای تأیید ایمیل (۳۰ دقیقه) و بازیابی (۱۵ دقیقه، ۵ تلاش)، شمارهٔ موبایل اختیاری برای بازیابی پیامکی.
- مالک: نقش `owner/super_owner`؛ کنسول با رمز محلی باز می‌شود و برای عملیات سروری (مثل اتصال ایمیل/پیامک) باید با حساب مالک به سرور وارد شود.

## استقرار

- فرانت‌اند: GitHub Pages از شاخهٔ `main` و ریشهٔ مخزن؛ کش سرویس‌ورکر با هر انتشار bump می‌شود (`wt-v113` این انتشار).
- بک‌اند: هر میزبان Node؛ برای ارسال واقعی ایمیل/پیامک باید میزبانی شود و `runtime-config.json` به آن اشاره کند.

## اعلان‌ها، نظرسنجی و پشتیبانی (بخش ۲۶–۲۸)

اعلان‌ها:

- همهٔ اعلان‌ها از یک مسیر می‌گذرند: `deliverNotice` در `server/notify.js`. ابتدا دسته/اتاق/سرور بررسی می‌شود، بعد رکورد در `notifications` نوشته می‌شود و اگر کاربر حداقل یک سوکت زنده داشته باشد `delivered_at` پر می‌شود. یعنی نشان «پوش شد» فقط وقتی است که واقعاً به دستگاه رسیده؛ در غیر این صورت «فقط درون‌برنامه».
- دسته‌های واقعی و تریگرها: `dm_message` و `mention` (پیام خصوصی)، `friend_request`/`friend_accept`، `room_invite` (قبول دعوت)، `room_activity` (پیوستن/خروج عضو، تغییر مدیر)، `poll`، `moderation` (گزارش)، `support_new`/`support_update`، `payment` (ثبت سفارش)، `security` (تغییر رمز/بازیابی).
- ضدتکرار: هر اعلان `dedupeKey` و پنجرهٔ زمانی دارد (حداقل ۳۰ ثانیه)؛ ارسال تکراری همان کلید در پنجره حذف می‌شود.
- سکوت دسته‌ای (`prefs[kind]=false`)، سکوت سراسری (`prefs.all=false`) و سکوت اتاق (`prefs.rooms[CODE]=false`) در سرور اعمال می‌شود؛ کلاینت فقط سوییچ‌ها را به PUT می‌فرستد و باید نقشهٔ `rooms` را حفظ کند چون کل شیء `prefs_json` جایگزین می‌شود.
- ساعت سکوت: اعلان ذخیره می‌شود ولی پوش نمی‌رود؛ بعد از پایان ساعت سکوت هم دوباره فرستاده نمی‌شود (تاریخچه درون‌برنامه می‌ماند).
- پوش مرورگر: فقط با اجازهٔ صریح کاربر (سوییچ «فعال‌سازی پوش») و فقط وقتی تب پنهان است؛ بدون اجازه هیچ `Notification` ساخته نمی‌شود. سرور زیرساخت Web Push (VAPID/endpoint) ندارد.

نظرسنجی:

- مخاطب = میزبان اتاق + اعضای فعال؛ ساخت/بستن/حذف فقط با مجوز مدیریت اتاق.
- قواعد رأی در سرور: تک‌انتخابی بودن، محدودیت اعضا، رد رأی تکراری (۴۰۹ `already_voted`)، رد رأی بعد از بستن/انقضا (`closesAt`).
- به‌روزرسانی زندهٔ نتیجه فقط شمارش خام است (بدون `mine` یا رأی کاربران دیگر) تا وضعیت رأی هر کاربر لو نرود؛ کلاینت شمارش را با رأی محلی خودش ادغام می‌کند.
- تاریخچهٔ نظرسنجی در تب «نظرسنجی» صفحهٔ اجتماعی با کد اتاق قابل بارگذاری است.

پشتیبانی:

- راهنما و پرسش‌های پرتکرار در `assets/data/help.json` (فارسی/انگلیسی) و جست‌وجوی کلاینتی؛ بدون سرور هم کار می‌کند.
- تیکت: دسته، اولویت (کم/معمولی/زیاد/فوری)، وضعیت (باز/در انتظار/حل‌شده/بسته)، پیام کاربر و کارمند، پیوست تصویر/PDF/TXT تا ~۴۰۰ کیلوبایت به‌صورت data URL.
- عملیات کارکنان فقط برای نقش‌های `moderator/administrator/owner/super_owner`؛ ارجاع فقط به کارکنان مجاز، تغییر وضعیت/راه‌حل با ثبت پیام سیستم و اعلان به صاحب تیکت.

## شکاف‌های شناخته‌شده

- GitHub Pages سرور اجرا نمی‌کند؛ کدهای ایمیل/پیامک روی سایت زنده فقط با سرور میزبانی‌شده ارسال می‌شوند.
- درگاه پرداخت واقعی هنوز وصل نشده؛ سفارش و اشتراک در سرور ثبت و مدیریت می‌شوند اما تسویهٔ بانکی فاز بعد است. بنابراین دستهٔ «اشتراک» تریگر واقعی ندارد؛ اعلان «پرداخت» هنگام ثبت سفارش ساخته می‌شود.
- مفهوم «سرور/Server» هنوز وجود ندارد؛ دستهٔ «فعالیت سرور» با «فعالیت اتاق» پوشش داده شده است.
- Pub/Sub و کارگر پس‌زمینه برای مقیاس افقی وجود ندارد.
